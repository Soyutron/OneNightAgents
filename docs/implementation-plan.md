# OneNightAgents 実装計画（MVP の範囲・実装順序・検証方法）

本書は MVP の範囲、実装順序、観察駆動の改善サイクル、最初に検証する仮説を定める。
設計の根拠は [game-design.md](game-design.md)、[architecture.md](architecture.md)、[agent-design.md](agent-design.md) を参照。

- 作成日: 2026-10-14（改訂 1: Deep Agents を初期版から採用、LangSmith による観察駆動の改善を基本方針に変更）
- ステータス: 設計案（未実装）

---

## 1. 開発の基本方針

1. **まず動くものを作る。** 「5 人の Deep Agent プレイヤーが 1 ゲームを完走し、LangSmith に 1 トレースが残る」状態を最短で作る（Step 1〜3）。
2. **観察してから改善する。** プロンプト、ハーネスの機能、ミドルウェアの変更は、必ずトレースと JSONL の計測を見てから行い、結果を実験ノートに残す。
3. **Deep Agents の機能は 1 つずつ有効化する。** 有効化前後で同じ seed 集合を実行し、挙動・時間・トークンの差を見る。
4. **完成度より反復回数。** テストは `rules` と情報隔離を必須にし、他は動いてから増やす。

## 2. MVP の定義

### 2.1 MVP に含める

| 領域 | 内容 |
| --- | --- |
| ルール | 日本版基本ルール（村人・人狼・占い師・怪盗、カード N+2、中央 2 枚、既定 5 人） |
| 進行 | 夜 → オープニング → 自由ラウンド（パス・応答権）→ 投票 → 判定 → 全公開（LangGraph） |
| GM | Python。決定的。seed 固定 |
| プレイヤー | **`DeepAgentPlayer`**（`create_deep_agent` + 行動ツール + 仮想 FS のメモ + `ModelCallLimit` + `ModelRetry`）、`RandomPlayer`（テスト・ベースライン） |
| 推理メモ | エージェント自身が `/notes.md` に書く。夜明け後・投票前に GM が更新を要求。スナップショットをログ |
| ペルソナ | YAML の性格プロンプトを system prompt に注入 |
| LLM 層 | 1 モデル共有、逐次、`num_ctx` 明示、タイムアウト、計測ミドルウェア |
| 観測 | LangSmith トレース（ゲーム単位、メタデータ付与）+ `runs/<id>/` の JSONL |
| 観戦 | CLI にイベント逐次表示。`--reveal` で推理メモも表示 |
| バッチ | `bench --games N` と簡易集計（勝率・フォールバック率・ステップ数・レイテンシ） |
| 実験ノート | `docs/experiments/` の様式 |
| テスト | `rules`、情報隔離、`mailbox`。スクリプト全ゲームは動いてから |

### 2.2 MVP に含めない（段階的に追加）

| 領域 | 時期 |
| --- | --- |
| `SimpleLLMPlayer`（ハーネスなしの比較用） | 第 2 段階の最初（比較実験に必要） |
| `permissions`、`skills`（役職別戦術） | 第 2 段階 |
| 入札方式のターン制御 | 第 2 段階（ラウンド制で不自然さが観察されたら） |
| 並列推論（`OLLAMA_NUM_PARALLEL`） | 第 2 段階 |
| エージェント視点のストリーミング観戦 | 第 2 段階 |
| サブエージェント（反論役）、`memory` + `StoreBackend`（ゲーム横断の学習メモ） | 第 3 段階 |
| 人間プレイヤー（`interrupt_on` / `interrupt()`） | 第 3 段階 |
| 吊人・米国版役職 | 第 3 段階以降 |
| Web UI / 複数 PC | 将来 |

## 3. 実装順序

### Step 0: 技術スパイク（1〜2 日、使い捨てスクリプト）

目的: Deep Agents + Ollama の組み合わせが動くかと、テンポの桁を知る。

1. Ollama で候補モデル（例: qwen3.5:9b、gemma4:12b、gpt-oss:20b、qwen3:8b。VRAM に合わせる）を取得し、`ollama ps` で 100% GPU を確認。
2. `ChatOllama.bind_tools` で 2〜3 個のダミーツールを渡し、ツール呼び出しの成功率（引数 JSON の妥当性、不要な呼び出し）を 20 プロンプトで測る。
3. `create_deep_agent(model=ChatOllama(...), tools=[speak], backend=StateBackend())` の最小構成で「メモを `/notes.md` に書いてから `speak` を呼ぶ」指示を実行し、ステップ数・レイテンシ・成功率を測る。`LANGSMITH_TRACING=true` でトレースを確認し、ハーネスの system prompt の長さとツール定義のトークン数を見る。
4. 日本語の短文生成の自然さを目視評価（5 段階）。`reasoning=False` の効き目を確認。
5. `num_ctx=16384` の VRAM 使用量。足りなければ `OLLAMA_KV_CACHE_TYPE=q8_0`。
6. 結果を `docs/experiments/000-spike.md` に記録し、既定モデル・`llm_timeout_sec`・`model_call_limit` を仮決めする。

合格の目安: ツール呼び出し成功率 90% 以上、1 判断（最大 4 ステップ）の p95 が 30 秒以下、日本語が破綻しない。満たすモデルがなければ、英語プロンプト + 日本語出力、モデルサイズ変更、`SimpleLLMPlayer` 先行のいずれかを選んでから進む。

### Step 1: ルール層（LLM なし、半日〜1 日）

- `game/models.py` `game/rules.py`。単体テスト（配役、夜の解決、集計、判定、検証）。

### Step 2: メッセージ生成・スケジューラ・エンジン（1〜2 日）

- `game/messages.py` `game/scheduler.py` `engine/graph.py` `engine/recorder.py` `players/scripted.py` `cli.py play`。
- `RandomPlayer` 5 人で 1 ゲームが完走し `events.jsonl` が出る。情報隔離テスト。
- `LANGSMITH_TRACING=true` で GM グラフのトレースが取れることを確認（この時点ではモデル呼び出しなし）。

### Step 3: DeepAgentPlayer（2〜3 日）— ここで「動くもの」が完成

- `players/mailbox.py`（行動ツール）、`players/deep.py`、`players/prompts.py`、`llm/ollama.py`、`llm/metrics.py`。
- 5 人の `DeepAgentPlayer` で 1 ゲーム完走。LangSmith に「ゲーム → ノード → プレイヤー → モデル/ツール」の階層トレース。`agent_steps.jsonl` に計測。
- 観戦表示と `--reveal`。
- `GenericFakeChatModel` でのプレイヤーテストは、動いてから追加。

### Step 4: 観察と最初の改善サイクル（継続）

Step 3 のトレースを読み、以下を順に観察・改善する。各項目を実験ノート 1 件にする。

| # | 観察項目 | 見る場所 | 改善の候補 |
| --- | --- | --- | --- |
| 1 | 行動ツールを正しく呼ぶか（呼ばずに文章で答えないか） | ツール呼び出し run、再要求率 | system prompt の提出手順、ツール description |
| 2 | 1 判断のステップ数と内訳（メモ読み・書き・提出・確認） | エージェント run の子 run | `model_call_limit`、「必要なときだけメモ」の指示 |
| 3 | `/notes.md` を書くか、内容が推理として妥当か | `write_file` 引数、`notes_updated` | メモの雛形を system prompt に置く |
| 4 | 履歴の成長と要約の発火 | `prompt_eval_count` の推移、Summarization run | `num_ctx`、要約閾値、差分メッセージの圧縮 |
| 5 | 人狼が騙るか、占い師が CO するか、応答ターンで答えるか | `utterance` ログ | ペルソナ、ルール要約の表現 |
| 6 | 投票理由が議論を参照しているか | `vote.reason` | 投票前のメモ更新要求の文面 |
| 7 | 時間とトークンの内訳（ハーネスの system prompt・ツール定義の固定コスト） | モデル run の token usage | FS ツールの許可リスト縮小、プロンプト短縮 |

### Step 5: ペルソナ・バッチ・簡易分析（1〜2 日）

- `configs/personas/`、`bench --games N --seeds 1..N`（LangSmith はプロジェクト名を分けるか無効化）、`analysis/summarize.py`。
- 同一 seed 集合で設定 A/B を比較する表が出る。

### Step 6: 人間参加に向けた観察項目（AI 同士のベンチで測る、第 3 段階の前提）

人間が 1 席に入ったとき「相手として面白い」ために必要な性質を、人間を入れる前に AI 同士のベンチで測る。022 までの改善は「村側が正しい情報に乗るか」を見てきたが、人間は固定ルールや癖を数ゲームで見抜いて利用するため、観点を「嘘や癖に対して崩れないか」に移す。各項目を実験ノート 1 件にする。

| # | 観察項目 | 測り方 | 改善の候補 |
| --- | --- | --- | --- |
| 1 | 固定ルールの搾取: 対抗のない嘘の占い師 CO（018 で信頼する決まり）に村側が乗ってしまわないか | 嘘の占い師 CO を出す scripted な人狼を 1 席混ぜ、村側の票が人狼に向く割合を基準線と比べる。summarize に「嘘 CO の配役」の分類を足す | 「対抗がないから信頼」を「CO の内容と他の情報の整合」で判断する表現に寄せる |
| 2 | 応答の質: 宛先付きの問いに具体的に答え、前の発言との矛盾を指摘できるか | 応答ターンの発言が問いに答えているかの目視、なぞり率 | 発言の文数制限、思考の上限（022 の次の仮説 1） |
| 3 | 癖（tell）: 役職ごとに発言が固定していないか（怪盗は CO しない、人狼は「態度が強引」で返す等） | 役職別に初手発言と投票理由の文面を分類し、偏りを見る | ペルソナを bench で使い、人格差が発言に出るかを 5.4 の軸で比較 |
| 4 | 人狼の嘘の筋: 嘘 CO が議論の中で矛盾を突かれずに通るか | 嘘 CO をした人狼が処刑される割合、嘘の内容が占い結果や CO と整合しているかの目視 | 役職別スキル（第 2 段階、人狼・怪盗から） |

最初の実験は 1 とし、023 として「嘘の占い師 CO を出す scripted な人狼」を混ぜる。人間席の入力制御（タイムアウト、催促、投票への早送り）と終了後の種明かし表示は、第 3 段階の人間プレイヤーの実装項目に含める。

### 第 2 段階（MVP 後）

- `SimpleLLMPlayer` を追加し、同一モデルで `DeepAgentPlayer` と比較（テンポ・勝率・騙り率）。ハーネスの効果を切り分ける。
- `permissions`（`/notes/**` 以外 deny）と `skills`（役職別戦術）を有効化し、読み込み率と効果を観察。
- 入札方式スケジューラ、並列推論、エージェント視点のストリーミング観戦、`SqliteSaver`。

### 第 3 段階

- サブエージェント（投票前に「反論役」へ委譲）、`memory` + `StoreBackend`（ゲーム後の振り返りを次ゲームで読む）、人間プレイヤー（Step 6 の項目を満たしてから。入力のタイムアウトと催促、投票への早送り、終了後に AI のメモと投票理由を見せる種明かしを含む）。

## 4. 実験ノートの様式（`docs/experiments/NNN-<slug>.md`）

```markdown
# NNN: <タイトル>
- 日付 / 対象ステップ
## 仮説
（例）発言ターンで FS ツールを見せないと、1 判断のステップ数が 1.8 → 1.2 に減り、テンポが 30% 改善する。騙り率は変わらない。
## 設定
- config / プロンプト / ミドルウェアの差分、モデル、seed 集合
## 観察
- トレース URL（代表例 2〜3 件）
- 集計表（ステップ数、p50/p95、トークン、フォールバック率、勝率、騙り率）
- 気づいたこと（トレースで見た具体的な挙動）
## 結論
- 採用 / 不採用 / 条件付き
## 次の仮説
```

## 5. 検証方法

### 5.1 自動テスト

[architecture.md](architecture.md) 12 節。LLM なしのテストを常時実行、実 Ollama の結合テストは手動。

### 5.2 テンポの評価（目標は仮。Step 0 で見直す）

| 指標 | 目標 |
| --- | --- |
| 1 判断のレイテンシ p95 | 30 秒以下 |
| 1 判断のモデル呼び出し回数（平均） | 2 以下 |
| 1 ゲーム総時間（5 人・自由 2 ラウンド） | 10 分以内 |
| 行動未提出率 + フォールバック率 | 5% 未満 |
| ツール引数の妥当率 | 90% 以上 |

### 5.3 ゲームとしての成立（目視）

- 占い師が CO するか／しない選択もあるか。
- 人狼が嘘の CO や疑いの誘導をするか。[ASCII.jp の事例](https://ascii.jp/elem/000/004/207/4207849/)で見られた「自分から人狼だと明かす」が起きないか。
- 応答ターンで質問に答えているか。
- 同じ内容の繰り返しがないか。
- 投票理由が議論を参照しているか。

### 5.4 比較実験

- seed 集合（例: 1〜30）を固定し、設定 A/B を各 30 ゲーム。
- 軸: モデル、温度、ペルソナ、ラウンド数、スケジューラ、`DeepAgentPlayer` vs `SimpleLLMPlayer`、スキル有無、メモ更新頻度。
- 指標: 陣営別勝率、総時間、ステップ数、フォールバック率、嘘 CO 率。`RandomPlayer` 同士をベースラインに。

## 6. 最初に検証すべき技術的仮説（優先順）

1. **ローカルのツール対応モデル（8B〜20B 級）が Deep Agents ハーネス下で、行動ツールを正しく呼び、`/notes.md` を扱える。** 崩れた場合: モデル変更、FS ツールをさらに絞る、行動提出を `response_format` 方式に変える、`SimpleLLMPlayer` を先行させる。
2. **1 判断が最大 4 ステップ・p95 30 秒以内に収まり、1 ゲームが 10 分以内。** 崩れた場合: 発言ターンのメモ操作を禁止、`model_call_limit` を下げる、ラウンド数・人数を減らす、thinking 無効化。
3. **プレイヤーのスレッド（履歴累積）が `num_ctx=16384` に収まり、要約が発火しても推理が崩れない。** 崩れた場合: 差分メッセージの圧縮、要約閾値の調整、判断ごとにスレッドを作り直す方式。
4. **ラウンド制 + パス + 応答権で、質問・反論・沈黙を含む議論が成立する。** 崩れた場合: 入札方式。
5. **「嘘をついてよい」の明示で人狼が騙る。** 崩れた場合: ペルソナ・スキルで戦術を与える。

## 7. 最大の技術的リスク

**ローカルの小型モデルが Deep Agents のツール呼び出しループを安定して回せるか、そしてそれがテンポに収まるか。** Deep Agents の公式評価はクラウド大型モデル中心で、ローカル小型モデルの実績は示されていない。対策は Step 0 の実測、`ModelCallLimit` と決定的フォールバックによる「止まらないゲーム」、そして `SimpleLLMPlayer` という退避先を第 2 段階の最初に用意すること。

副次的リスク:

- Deep Agents / LangChain / LangGraph の API 変化が速い。本設計は 2026-10-14 時点の公式ドキュメントに基づく。実装時に参照 URL を再確認する。
- LangSmith はクラウドサービスで、トレースにプロンプト全文が送られる。ゲームデータなので許容するが、大量バッチでは無効化する。

## 8. リポジトリに関する注記

- 現状のリポジトリには本プロジェクトのコードはない。別プロジェクト（taxforge）由来の `Makefile`・`AGENTS.md`・UI 向けスキル・`.mcp.json` の UI/DB 系サーバー・`CLAUDE.md` の Issue トラッカー参照は 2026-10-14 に削除済み。Step 1 着手時に `Makefile` を本プロジェクト用（`uv sync` / `uv run pytest` / `play` / `bench`）に新規作成する。`.gitignore` には `runs/` と `.env` を設定済み。`.mcp.json` には `docs-langchain` / `reference-langchain` / `langsmith-apac` を残している。
