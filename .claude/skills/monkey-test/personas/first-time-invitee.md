# 初めての招待者

**ログイン**: しない。未ログインで始める。招待は事前に owner(`soyu@example.test`)として発行し、
画面の「リンクをコピー」で控えてからサインアウトする。宛先は `monkey-<日時>@example.test`。
ローカルでは招待メールは送られない(Mailpit に来るのは signup の確認コードだけ)。
作ったユーザーはローカル DB に残る(`make db-local-reset` は検証ユーザーごと消すので無人ループの既定巡回には入れていない)。

**性格**: 手順を読まない。コードを間違える。ページを戻る。同じリンクを 2 回開く。パスワードを短くする。

**狙い**: signup と招待受理の経路。`/signup` → OTP → パスワード設定 → `/invitations/<id>` → 受理 → チャット。
招待ページ着地直後の RPC 401(既知・未解決)の再現条件を探す。

**OTP の取り方**: Mailpit の API。`curl -s 'http://127.0.0.1:54324/api/v1/messages?limit=5'` で一覧、
`curl -s http://127.0.0.1:54324/api/v1/message/<ID>` で本文。6 桁の数字がコード。
確認コードの再送は同一メールで 60 秒に 1 回しか受け付けない。

**癖**:

1. 招待リンクを未ログインで開く → `/signup?next=/invitations/<id>` に飛ぶか。`next` を保ったまま進めるか。
2. 宛先と違うメール(`someone-else@example.test`)で signup を試す。拒否の文言を見る。
3. 正しいメールで確認コードを要求 → 間違ったコードを 2 回 → 正しいコードを入れる。
4. パスワードに 5 文字を入れる(最小は 6)。
5. パスワード設定後の遷移で `/invitations/<id>` に着地した直後の network を見る。`invitation_preview` が 401 なら
   即記録し、reload で直るかを見る。
6. 受理ボタンを `browser_run_code_unsafe` で 2 回連続クリックする。
7. 受理後にブラウザの戻るで招待ページへ戻り、再度受理する。
8. 受理後にチャットで 1 通送る(無マーカー)。サイドバーの組織名が正しいか。
9. 別タブで同じ招待リンクを開く(受理済みの表示になるか)。
10. サインアウトし、同じメールとパスワードで `/login` からログインできるか。

**やらないこと**: 組織の作成、他人のロール変更、`invitee@example.test` 宛の招待。
